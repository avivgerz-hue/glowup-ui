# Try a reproducible UI redesign comparison

A small independent challenge, not a completed benchmark. Use disposable fixture copies; no private app or testimonial is required.

**Question:** Can the agent change the visual hierarchy of an existing dashboard while keeping its original interactions?

1. Use the bundled [Plotline before source](../demo/before) in two disposable directories from the same exact repository commit. Keep the host, model, effort, tools, permissions, seed data and time budget identical. Neither session sees the other's result. Record the commit and actual runtime.
2. Save matching original desktop/phone captures and run the existing tests/build. Keep existing failures visible. Install the published v0.1.1 skill only into the treatment directory using the README's pinned project command. Do not layer installers or load a global Glowup copy into the control. If isolation cannot be established, report that the comparison is invalid.
3. Give both agents this same task: “Redesign the existing project dashboard across its existing screens. Make the primary task and information hierarchy clear, improve navigation, typography and phone composition, and keep the current routes, content, data and interactions. Implement the changes, run the existing checks, and inspect matching desktop and mobile views. Report incomplete or unverified work.” Explicitly request `$glowup-ui` only in the Codex treatment wrapper (or the host's documented equivalent), and confirm complete instruction/reference delivery. A name in a listing is insufficient.
4. Run the same original tests/build and primary interaction in both results. Capture equal 1440×900 and 390×844 views with the same state, theme and scroll. Do not hand-edit one result before judging it. Keep dependencies and actual runtime/token metrics separate; leave unavailable metrics blank.
5. Randomize X/Y for someone who did not build either result. Ask which has clearer hierarchy, navigation, typography, phone composition and cross-screen consistency; permit ties. Evaluate functionality separately. Keep the key private until opinions are recorded. One trial is not proof of consistent superiority.

The [existing independent guide](INDEPENDENT-TESTING.md), [paired harness](../benchmarks/PAIRED-EVALUATION.md) and [optional feedback form](feedback.md) supply the details. Share sanitized results voluntarily, including failures; do not ask for private projects, secrets or praise. No developer trial was executed as part of this distribution sprint.
