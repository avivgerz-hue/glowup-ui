# Glowup UI 0.2.0-dev.2 candidate

This is an implementation candidate, not a published release. Public installation pins remain on v0.1.1. Existing tags are unchanged. No claim of universal compatibility, independent human preference, guaranteed preservation or design superiority follows from this work.

## What changes

The integrated skill already had polish/recompose/reframe, product alternatives, screen coverage, behavioral outcome checks and bounded rendered critique. This candidate preserves those capabilities and adds concrete input to design decisions:

- Two original instructional compositions: a dominant working collection with supporting context, and decision-order selection with an accurate summary. Each uses identical content before/after, structural fragments, phone ordering, screen adaptations and rejection cases. They are hand-authored studies, not agent-generated outcomes.
- Problem-routed studies, with optional CLI retrieval through `design-brief.mjs --problem hierarchy|selection`; no automatic catalog loading, remote search, new runtime or mandatory planning artifact. The ordinary command remains valid; REFINE/polish returns no study.
- Clear distinction between protected product/brand commitments and incidental starter styling that a broad redesign may replace. Explicit layout, palette or type constraints still win.
- Source validation, installed-byte verification, exact version output and stage-driven terminal progress. No fake delays, telemetry or dependency. Existing conflict/backup/removal semantics remain.

## Reproduce engineering checks

Run `npm test` and `node bin/glowup-ui.mjs validate`. Under Node 22 with the explicitly installed benchmark dependencies/browser, run the existing browser suite and `node benchmarks/studies.mjs`. `--write` deliberately regenerates study captures; the default checks sources, committed capture hashes, retained visible content and document overflow without replacing them. The studies are not aesthetic scores.

The current browser harness uses Playwright's default Chromium launch configuration inside the execution environment. Playwright defaults its Chromium OS sandbox off; do not describe that as an enabled browser sandbox. No host permission, filesystem sandbox or network policy was changed. Browser checks are for trusted local fixtures, not arbitrary untrusted pages.

## Evaluation boundaries

Native Codex 0.163.0 was tried again with `--ephemeral --sandbox read-only`; it failed before a model turn: `failed to initialize in-process app-server client: Read-only file system (os error 30)`. No credentials were copied or permissions weakened. An authenticated outer session does not establish native CLI activation.

The exact-commit six-cell preparation reuses the existing finance and booking fixtures, identical task/app hashes, and independent control/current/candidate workspaces. Fresh-context in-session agent runs are an alternative runner: they cannot certify Claude/Codex/Copilot native loading. Their shared filesystem is an instruction boundary, not a security isolation boundary; exact provider model IDs, token usage and tool counts may be unavailable. Preserve those limitations, ties and losses. Concurrent wall times are not a calibrated speed benchmark.

## Executed outcome

[Sanitized results](v0.2-results.json) record eight actual app implementations: control/current/dev.1 for finance and booking, then dev.2 reruns on both unchanged starting apps. The same task and starting-app hashes were retained within each product. All 56 original fixture tests passed across those outputs; all four booking builds passed (the finance fixture has no build script). A common browser collector exercised real flows, captured 112 desktop/phone views and found no document overflow, unnamed controls, blocked controls or multiple main landmarks in those final views. These narrow findings do not establish complete accessibility or visual quality.

The first candidate did not retrieve its new studies. Routing was corrected; both dev.2 runs documented complete reads of the relevant study. Finance implemented a genuinely different, transaction-led desktop composition with compact balance context; booking applied selection/summary relationships. This is identifiable workflow influence in the in-session runner, not native activation certification.

| Blinded model comparison | Result |
|---|---|
| dev.1 vs current, finance | Current preferred marginally |
| dev.2 vs no skill, finance | Candidate preferred marginally |
| dev.2 vs current, finance | Current preferred marginally |
| dev.2 vs no skill, booking | Tie |
| dev.2 vs current, booking | Tie |

These are five fresh-context **model** assessments, not independent human evaluations. There were no numeric quality scores. Finance's desktop collection gains trade against phone summary visibility; booking has opposing desktop density and phone readability strengths. The outcome does **not** establish a substantial or consistent design advantage. One trial per cell cannot establish reliability or variance. Human X/Y forms remain empty and separate from model reviews.

Recorded implementation intervals were roughly 7–10 minutes where timestamps existed; intake was not fully clocked and one current-booking agent report was interrupted. Its saved implementation, tests/build and browser captures were independently checked without manually improving it. No calibrated speed comparison, exact provider model ID, token count or tool-call count is available. New application dependencies: zero.

## Engineering checks and corrections

- 170 repository tests under Node22 and canonical skill validation passed. Existing CREATE/REFINE browser contracts, three-app quality checks, chat journeys, source-hashed examples and new study/Gather checks were executed. Six dependency-lock audits plus the starter audit reported no vulnerabilities.
- A packed candidate installed, executed its installed helper and removed safely; a real PTY exercised progress. The actual GitHub-source dev.2 command below installed both intended project payloads with matching hashes and removed them. Native activation remains unverified.
- Source-hashed text now keeps LF on Windows. Benchmarks resolve Playwright from their own package instead of depending on a host installation. Hosted checks must be verified on the final PR head.
- Final review reproduced a false-provenance pass on an occupied preview port. The collector now rejects occupied ports, monitors child exit, checks served source bytes and stops only its own process. Four regression tests cover collision, correct source, wrong source/exited child and evidence overwrite. All eight implementations were recaptured with these checks. Of 112 images, 109 were byte-identical to the earlier sets; three phone recaptures differed by only 6–18 pixels, with unchanged layouts. The original model-reviewed sets remain preserved.
